## 3. Response Model Hierarchy

The standardized API response envelope layouts are structured using composition rather than legacy class inheritance:

```
                  BaseModel (Pydantic v2)
                             │
       ┌─────────────────────┼─────────────────────┐
       ▼                     ▼                     ▼
 ApiResponse[T]        PagedResponse[T]      ErrorResponse
 (Standard Success)    (Paginated Collection)(Failed Call)
       │                     │                     │
       ├─► data: T           ├─► data: list[T]     ├─► data: Any (e.g. error list)
       ├─► success: true     ├─► success: true     ├─► success: false
       ├─► message: str      ├─► message: str      ├─► message: str
       ├─► request_id: str   ├─► request_id: str   ├─► request_id: str
       ├─► timestamp: str    ├─► timestamp: str    ├─► error_code: str
       └─► meta: Any         └─► meta: PaginationMeta
```

## 4. Response Builder Design

The [ResponseBuilder](file:///e:/TaskSyncEnterprise/backend/app/core/response_builder.py) utility manages the instantiation of the response envelopes dynamically:

*   **`success(data, message, meta)`:** Returns an `ApiResponse` with `success=True` and status 200.
*   **`created(data, message, meta)`:** Returns an `ApiResponse` representing newly created resources (status 201).
*   **`updated(data, message, meta)`:** Returns an `ApiResponse` indicating record modifications.
*   **`deleted(message, meta)`:** Returns an `ApiResponse` indicating record deletions.
*   **`no_content()`:** Returns a FastAPI `JSONResponse` with status `204` and correct correlation headers (`X-Request-ID`), leaving the response body empty.
*   **`pagination(items, page, size, total, message)`:** Returns a `PagedResponse` containing collection arrays and auto-computed total pages boundaries.

## 5. Pagination Architecture

Standard pagination structures map database aggregates directly into standard `PagedResponse[T]` schemas:

```mermaid
graph TD
    DB[(MS SQL Server)] --> |Retrieve Page & Count| CRUD["CRUD Engine (app/crud/*)"]
    CRUD --> |List[ORM Models] & Total Count| Router["Router (app/routers/v1/*)"]
    Router --> |Pass items, page, size, total| PagedResponse["PagedResponse[T]"]
    
    subgraph Serialization Envelope
        PagedResponse --> |data| Items["data: list[T]"]
        PagedResponse --> |meta| Meta["meta: PaginationMeta"]
        Meta --> Page["page: int"]
        Meta --> Size["size: int"]
        Meta --> Total["total: int"]
        Meta --> Pages["pages: ceil(total / size)"]
    end
```

## 6. Generic Model Usage

By leveraging Pydantic v2's native support for Python typing Generics (`Generic[T]`), the response models preserve schema validation rules and type safety:

```python
from typing import Generic, TypeVar
from pydantic import BaseModel

T = TypeVar("T")

class ApiResponse(BaseModel, Generic[T]):
    success: bool = True
    data: T | None = None
```

When FastAPI generates the OpenAPI specification (Swagger UI), it inspects the generic parameter `T` (e.g. `ApiResponse[EmployeeResponse]`) to render the exact model schema structures in the Swagger docs instead of displaying generic, opaque objects.

## 7. Backward Compatibility

To guarantee zero breaking changes across the codebase:
1. **Incremental Adoption:** Existing endpoint routers continue to return raw dictionaries, lists, or custom schemas. They are unaffected by the presence of the new response structures.
2. **Standard Payload Fields:** The new envelopes do not remove any existing fields. The response builder automatically binds request correlation IDs from context variables, maintaining correlation traces.
3. **No Migration Needed:** Database mappings and Alembic schema objects are unaffected.

## 9. Migration Strategy

To gradually transition endpoints to the new Enterprise Response Architecture:

1. **Phase 1: Additive Onboarding**
   *   Introduce the response builder schemas and utilities without updating routers (Completed).
2. **Phase 2: Router Pilot Adoption**
   *   Refactor standard lookup endpoints (e.g., `health` status probes or `auth` info router) to return wrapped values via `ResponseBuilder.success(...)`.
3. **Phase 3: Paginated Routers Conversion**
   *   Refactor list endpoints (e.g., `departments` or `teams` listings) to use `build_pagination_response(...)`.
4. **Phase 4: Full Codebase Wrap**
   *   Wrap all remaining CRUD modification routers (created, updated, deleted) in standard builder envelopes.

## 10. Recommendations for P3.2-004

For the next phase (P3.2-004), we recommend:
1. **FastAPI Custom Route Middleware:** Implement a custom `APIRoute` class in FastAPI to intercept successful endpoint handlers and wrap payloads in standard `ApiResponse` envelopes automatically, eliminating the need to modify return statements in every router manually.
2. **Correlation Header Middleware:** Add a response-side middleware to always inject the `X-Request-ID` correlation ID directly in HTTP response headers.
