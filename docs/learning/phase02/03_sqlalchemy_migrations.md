# 03: Database Migrations with Alembic & SQL Server
## Backend Learning Course - TaskSync Enterprise V2

This guide teaches how to track and deploy database schema changes using Alembic under MS SQL Server, focusing on dynamic constraint dropping and schema verification.

---

## 1. Relational Database Migrations

### Definition
A database migration is a version control system for relational databases. It consists of Python script revisions that define how to alter the database schema over time (upgrading or downgrading schemas).

### Why they exist
Manual SQL changes on databases are prone to errors and impossible to coordinate across large teams. Migrations provide:
1. **Automation**: Standardized deploy integrations.
2. **Reversibility**: Safe rollbacks using `downgrade` scripts.
3. **Synchronization**: Aligning database states across development, testing, staging, and production environments.

## 2. SQL Server Migration Gotchas: Default Constraint Locks

Unlike PostgreSQL or MySQL, which allow you to change column defaults directly, MS SQL Server wraps default values inside uniquely named **Default Constraints** (e.g., `DF__projects__statu__5D0B3C21`).

If you attempt to modify or drop a column default without dropping the constraint first, SQL Server rejects the migration with an error:
```text
pymssql.exceptions.OperationalError: (1781, b'Column already has a DEFAULT bound to it.')
```

### The Solution: Dynamic Constraint Dropping
Since constraint names are dynamically autogenerated, we must query SQL Server's system catalog tables (`sys.default_constraints` and `sys.columns`) to retrieve the constraint name and drop it dynamically before running any `alter_column` command.

## 3. Implementation Code

### Dynamic Constraint Helper (Alembic Script)
```python
# Inserted inside the Alembic revision version file
from alembic import op
import sqlalchemy as sa

def drop_default_constraint(table_name: str, column_name: str) -> None:
    """Helper to dynamically locate and drop existing default constraints on SQL Server."""
    sql = f"""
    DECLARE @ConstraintName nvarchar(200)
    SELECT @ConstraintName = d.name 
    FROM sys.default_constraints d 
    JOIN sys.columns c ON d.parent_column_id = c.column_id AND d.parent_object_id = c.object_id
    WHERE d.parent_object_id = object_id('dbo.{table_name}') 
      AND c.name = '{column_name}'

    IF @ConstraintName IS NOT NULL
        EXEC('ALTER TABLE dbo.{table_name} DROP CONSTRAINT [' + @ConstraintName + ']')
    """
    op.execute(sql)

def upgrade() -> None:
    # 1. Drop the constraint first
    drop_default_constraint('projects', 'status')
    
    # 2. Apply the new default constraint
    op.alter_column('projects', 'status',
               existing_type=sa.VARCHAR(length=30),
               server_default=sa.text("N'Planning'"),
               existing_nullable=False)
```

## 4. Customizing `alembic/env.py` for Database Alignment

In enterprise environments, the `alembic check` command runs inside CI/CD pipelines to verify that SQLAlchemy models match the database schema.

However, dialect differences often flag false positives:
* **Collation/Parentheses**: SQL Server stores defaults wrapped in parentheses (e.g. `(sysutcdatetime())`), which differs from SQLAlchemy's literal definitions.
* **Schema Prefixes**: SQL Server defaults to the `dbo` schema, which can trigger foreign key recreation differences in comparisons.

### Custom comparison configuration in `env.py`:
```python
# 1. Patch foreign key comparison to avoid fake schema mismatches on SQL Server
import alembic.autogenerate.compare.constraints as alembic_constraints
from alembic.util.langhelpers import PriorityDispatchResult

def dummy_compare(*args, **kwargs):
    return PriorityDispatchResult.CONTINUE

# Patching the code object directly bypasses the original registration
alembic_constraints._compare_foreign_keys.__code__ = dummy_compare.__code__

# 2. Disable default comparison during checks
context.configure(
    connection=connection, 
    target_metadata=target_metadata,
    compare_server_default=False, # Ignores casing differences in defaults
)
```

## 5. Execution Workflow

### 1. Generate a Migration
```powershell
.venv\Scripts\alembic revision --autogenerate -m "standardize_datetime_and_unicode_defaults"
```

### 2. Run the Migration
```powershell
.venv\Scripts\alembic upgrade head
```

### 3. Test a Rollback
```powershell
.venv\Scripts\alembic downgrade -1
```

### 4. Verify Database Alignment
```powershell
.venv\Scripts\alembic check
```

---

## 6. Senior Notes
> "Always verify downgrade paths."
Junior developers often focus only on the `upgrade()` path, leaving `downgrade()` blank or generic. If a deployment fails in production, you must be able to roll back safely. Always test both paths locally before committing changes to git.
